# Анализ новых журналов Купола

Источник — публичный `WhiteDots/Dome_RAG`, зафиксированная ревизия
`a16da2db079cdcb395e354383199effdf5a170b2`. Обработаны все журналы за
12–18 октября 2026 года: 21 файл, 196 037 410 байт, 10 080 минутных снимков,
2 478 событий, в том числе 275 действий, и 8 записей дневника. Некорректных
строк и нарушений порядка времени в этом наборе не обнаружено.

Получено 111 исторических эпизодов 20 классов. Минутные снимки дали 92
эпизода; ещё 19 добавлены по событиям, поскольку краткая тревога может
возникнуть и исчезнуть между снимками. Все 111 включены в локальную базу RAG,
дневник сохранён отдельно. Машинный манифест содержит полные данные; в
интерфейс достаточно передавать счётчики и краткие поля эпизодов.

## Что считается доказательством

Каждый эпизод содержит ревизию источника, SHA256 файла, номер строки,
временные метки, начальные/последние состояния и, при наличии, следующий
кадр без признака. Рядом расположенные действия приведены в окне ±5 минут
с указанием исходного `success`, исполнителя и команды. Это временная связь,
а не доказательство причины ремонта.

`CONDITION_CLEARED` — признак отсутствует в одном следующем снимке.
`EVENT_SIGNAL_CLEARED` — очищен флаг в журнале событий.
`EVENT_BURST_OBSERVED` — наблюдалась серия переключений.
`OPEN_AT_END` — до конца дневного файла не зафиксировано очищение.
`DATA_GAP` — непрерывность наблюдений нарушена. Ни один из этих исходов не
записывается как `VERIFIED_SUCCESS` в память автоматических ремонтов.
Дневниковые объяснения помечены `HUMAN_NARRATIVE_UNCORROBORATED`.

## Диагностические выводы для текущего агента

- Успешный ответ API не доказывает изменение линии, замка или станка.
  Нужны новые независимые наблюдения фактического состояния.
- Задержка дополнительных CO₂-датчиков достигает 900 секунд. Большинство
  старых показаний не опровергает текущий высокий CO₂. Сопоставлять время,
  физическое происхождение источников и фактический поток вентиляции.
- Дневник описывает настоящий рост CO₂ при отказе притока и отдельный случай
  одиночного ложного показания. Это разные гипотезы, а не один универсальный
  сценарий смены основного датчика.
- `webhook_state=COMPLETED` встречается при продолжающейся печати. Нужны
  `state`, `real_state`, прогресс и координаты; нельзя разрешать физический
  доступ к принтеру по одному webhook.
- Ошибка изоляции инвертора E09 связана в дневнике с сыростью, но это не
  разрешает считать её ложной и отправлять `reset_error` без проверки.
- Повторные сбросы аварии вытяжки могут не устранять механическую причину.
  Фактический поток важнее команды включения.
- Серия переключений обычного освещения наблюдалась рядом с шумом датчиков.
  Наводка — гипотеза автора дневника; текущую причинность нужно проверять.
- Рост утечки линии фрезера, тока вентилятора инвертора, потерь связи и воды
  в топливе требует анализа тренда. Значение 500 ppm для воды в топливе —
  наблюдавшийся исторический порог отказа, а не новый норматив безопасности.
- В истории есть настоящий пожар и краткие тревоги. Для опасного состояния
  приоритет имеют штатные меры безопасности, а не ожидание LLM и не сброс
  аппаратной защиты по похожему прошлому случаю.

## Интеграция

`kupol_agent.history.load_manifest()` возвращает манифест для интерфейса.
`compile_history(source_dir, output_dir=..., source_revision=...)` заново
разбирает локальную копию журналов потоком. Документы
`kupol_agent/knowledge/history_cases/*.md` автоматически индексируются
существующим `DocumentIndex` и BM25. Каждый фрагмент истории — данные без
исполнительных полномочий; актуальные факты и каталог API первичны.

Повторная сборка из подготовленной копии:

```powershell
python -m kupol_agent.history tmp/upstream_a16da2d --revision a16da2db079cdcb395e354383199effdf5a170b2
```

Сырые журналы не нужны в распространяемом комплекте: достаточно манифеста,
компактных фрагментов с происхождением и программы повторного анализа.

## Требования регламента

PDF требует DeepSeek V4 Flash в финальной игре, объявленные границы
автономности, журналирование значимых действий, проверку результата и
резервный сценарий. Аппаратные блокировки нельзя обходить или подавлять;
возобновление после аварийной остановки определяется разрешением
уполномоченного лица. Пользователь отдельно уточнил, что ручные команды
разрешены; ограничение старой вспомогательной инструкции не переносится в
приложение как запрет. История не меняет ни эти правила, ни текущие права API.

Проверки `tests/test_history.py`: два формата снимков, некорректный JSON,
null/NaN, порядок времени, разрыв данных, краткая тревога между снимками,
удаление ключей и отсутствие вымышленной успешности ремонта. Семь тестов
прошли на локальных синтетических данных; оборудование не использовалось.
