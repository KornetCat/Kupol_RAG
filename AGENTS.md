# Контекст проекта Купола

## Текущая архитектура и решения пользователя

- Основа — именно RAG-агент на DeepSeek, а веб-интерфейс — его оболочка. Перед ответом / планом искать инструкции, исторические эпизоды и проверенный опыт с учётом текущих аномалий и связей подсистем. Поиск усилен структурными признаками, балансом категорий, дедупликацией и условным отбором через DeepSeek. Другую модель эмбеддингов не добавлять.
- Пользователь отдельно разрешил прямое ручное управление API из страницы телеметрии, без DeepSeek. Это разовые команды через тот же исполнитель, текущий каталог и проверки безопасности, с аудитом `manual_api`. Такой вызов не становится постоянным указанием и не меняет состав автономных сценариев.
- Ручные указания разрешены и в соревновании. Режим «Указание на будущее» сохраняет их в отдельном доверенном контексте DeepSeek до явной отмены; они приоритетнее конфликтующего автоматического плана. Режим «Разовый запрос» выполняет вопрос или команду один раз: без сохранения в указаниях/overrides и без последующего использования текста в модельной истории. Факт действия и его результат остаются в техническом аудите по регламенту. Ни один режим не снимает аппаратные защиты и не повышает права API. Сохранять прерывание устаревших планов и единый исполнитель; у сохранённых указаний нет скрытого TTL.
- Пользователь разрешил передачу выбранной телеметрии, документации и опыта официальному API DeepSeek. Дополнительно явно разрешены имя, размер, SHA-256 и целевой станок загружаемого файла, выбранный фрагмент каталога и текст ручных указаний. Сам G-code и ключи в контекст модели не передавать. Полный файл передаётся только разрешённому API станка.
- Для фрезера использовать текущий список файлов и start_job; загрузку включать только если текущий каталог объявляет upload_file. Пользователь согласовал такой вариант. Отдельный интерфейс воспроизведения кризисов пока не нужен: приоритет — живой Купол.
- Пользователь предоставил подключение к виртуальному Куполу. Выполненные локальные тесты, проверки двойника и API DeepSeek не объявляются испытаниями физического оборудования. Для двойника использовать отдельный --data-dir, чтобы не смешивать его результаты с реальным контуром.
- Последнее указание пользователя: использовать доступную по ключу модель DeepSeek, точная версия не важна. Оба профиля по умолчанию используют deepseek-flash без блокировки V4/V4.1; фактически обслуженная модель записывается. Другие LLM/провайдеры не добавлять. Явная фиксация served ID остаётся необязательной настройкой. Буквальный текст п. 10.6 PDF не переписывать и не объявлять изменённым: отличие отражено в docs/REGULATION_COMPLIANCE.md.
- В ревизии upstream 5e1ec4854ddcccb12efc5f0b4a9bfd94fa190438 добавлены только пять химических DOCX; пользователь явно исключил их, автоматизация этого аппарата не предусмотрена. Химические задания не загружать в RAG и не добавлять их автоматизацию. Исходные журналы телеметрии этой ревизией не изменены.
- Наблюдаемый тренд тока вентилятора хранится отдельно от инцидентов/ремонтов как OBSERVED_TREND_UNCONFIRMED, с изоляцией среды и ограниченной числовой схемой. Поисковое использование не превращает такой тренд в доказанную поломку, инструкцию или успешный ремонт.
- Для запуска на месте сохранять весь функционал. Windows portable содержит официальный Python и зависимости; исходники и CLI остаются доступны. Ключи, пользовательские журналы и хранилища в распространяемые архивы не включать.
- GUI-настройка автономности сохраняет только три положительных конечных критерия потоков. Явное подтверждение безопасности относится к текущей сессии, профилю и команде, не включает auto и отзывается при потере связи. Не заменять обязательные минимумы выдуманными значениями или проверкой «поток больше нуля»; аппаратные защиты и повторный полный gate непосредственно перед отправкой сохранять.
- FAULT/START_FAILURE дизеля — наблюдаемый отказ запуска. CRANK обозначает этап; причину по нему не угадывать. Сценарий диагностики не запускает и не сбрасывает дизель. Исчезновение признака записывается как CONDITION_CLEARED_UNATTRIBUTED, без заявления успешного ремонта.

## Сохранённый опыт реального сеанса

Перед изменениями диагностики, WebSocket-клиента и исполнения учитывайте сохранённый реальный опыт:
`kupol_agent/knowledge/field_experience/2026-10-26_emergency_lighting.md`.
Машинная запись и источники: `kupol_agent/data/field_experience/2026-10-26_emergency_lighting.json`.

- 26.10.2026 пользователь подтвердил успешное физическое включение и выключение аварийного освещения. В проверенном сеансе команда 4 управляла `smart_panel_01`, линией 7, через `line_on` / `line_off` с `value: 7`. Перед новым действием сверяйте актуальный каталог, роль и назначение линии. IP-адрес не фиксировать в постоянной памяти сценария: пользователь задаёт актуальный адрес при подключении.
- `updated_at` округляется до миллисекунд, а `timestamp` кадра содержит большую точность. Учитывайте погрешность округления до 1 мс: строгое требование `timestamp >= updated_at` отвергало реальные свежие кадры. Сохраняйте проверки возраста, доступности узла и новых наблюдений после действия. Исправление уже есть в `emergency_light.py`; при улучшении основного агента проверьте аналогичные сравнения в `engine.py`.
- Различайте принятие команды API, подтверждение состояния новой телеметрией и подтверждение результата человеком. На этом endpoint напряжение 239.2 В и нулевые ток/мощность наблюдались и при ON, и при OFF; эти величины отдельно не доказывают свечение ламп.
- Печать этапов и конкретной причины отказа обязательна для ручных сетевых утилит: молчаливое отбрасывание кадров выглядело как подключение и отключение.
- В справочном чате официальный DeepSeek иногда возвращал корректный JSON только с answer, без пустых commands/sources, а иногда — повреждённый JSON. Для справочного запроса пропущенные пустые массивы нормализуются без выдуманных ссылок; допускается один повтор только ошибки формата с тем же ограниченным контекстом. Управляющие запросы остаются строгими и не повторяются. Ошибка чата должна сохраняться при очередном обновлении телеметрии. ARMED означает готовность защиты сработать, не отключение защиты.
- Ручной подтверждённый опыт доступен для RAG, но не расширяет автоматический список команд. Не приписывайте ему два постдействующих кадра или устойчивую автоматическую верификацию: сохранён один кадр после каждого действия плюс явное подтверждение пользователя. Ключи не включать в память и публикации.
